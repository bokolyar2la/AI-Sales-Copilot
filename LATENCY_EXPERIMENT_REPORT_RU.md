# Диагностика скорости и качества AI Sales Copilot

15 ноября 2026. Это измерительная итерация: основной режим генерации и инструкции продавца не заменены. Карта продаж Excel подготовлена отдельно и не подключена к рекомендациям.

## Вывод

**Thinking уже выключен.** Рабочий адаптер отправляет deepseek-flash, thinking.type=disabled, temperature=0.2, max_tokens=3000, timeout=45 секунд. Поэтому сравнение «текущий против без глубокого рассуждения» не образует двух разных режимов модели. Не создавали искусственный медленный baseline с включённым thinking.

Вместо фиктивного сравнения выполнен парный эксперимент: текущий буферизованный ответ против той же модели и параметров с stream=true. Поток нужен для измерения первого токена; клиентский интерфейс в обоих случаях ждёт полный проверенный JSON. Рабочий get_provider() по-прежнему использует diagnostic_stream=False.

На этой выборке потоковый вариант не даёт основания для переключения: небольшое различие медиан, один тайм-аут и одна блокировка, несколько содержательных ошибок. Около **99,2%** измеренного времени до карточки занимает обращение к провайдеру. Локальная подготовка, валидация и SQLite не являются главным узким местом.

## Методика

- 16 фиксированных синтетических ситуаций × 2 конфигурации = 32 измерения. Один проход каждой пары, порядок AB/BA чередуется. Запросы идут последовательно, без конкурентной нагрузки.
- Одинаковые реплики, исторический контекст, каталог, модель, промпт, лимит токенов и температура. Технические идентификаторы сессий и время создания различаются. Это контрольные точки, не полноценные ролевые разговоры; память предыдущих ходов не прогонялась моделью заново.
- Настоящий DeepSeek API, локальный FastAPI, SQLite и собранный React-интерфейс. Playwright управлял установленным Edge в headless-режиме, 1440×1000. Успешные браузерные образцы имели visibilityState=visible.
- Отсчёт браузера: непосредственно перед fetch отправки реплики → ответ API и JSON → React → две requestAnimationFrame. Это приближение до возможности отрисовки, не физический момент свечения пикселей на мониторе. Сеть браузер–localhost включена; время набора реплики не включено.
- p50/p95: линейная интерполяция, позиция (n−1)×p. При n=16 p95 очень чувствителен к одному хвостовому случаю. Доверительных выводов о стабильном преимуществе и конверсии не делаем.
- Кэш не сбрасывался. AB/BA снижает, но не исключает влияние кэша и меняющейся нагрузки провайдера. Длины выходов различаются, поэтому изменение времени нельзя приписать только транспорту.
- Первый ошибочный прогон стенда сохранён отдельно в latency-invalid-harness.json и **исключён**: модель и валидатор получали разные каталоги. Это ошибка эксперимента, не ошибка продукта и не часть 32 итоговых измерений.

## Из чего складывается время

Все значения ниже — миллисекунды, p50 / p95; потоковые этапы имеют 15 полных наблюдений, текущие — 16. Вложенные интервалы нельзя складывать: engine включает provider_requests, а server_response_ready включает engine и сохранения.

| Выбор базы знаний | 0.06 / 0.12 | 0.05 / 0.09 |

| Правила, источники и применение памяти | 0.57 / 1.20 | 0.43 / 1.21 |
| Обе записи SQLite суммарно | 17.61 / 23.04 | 15.35 / 19.41 |
| От получения запроса до готовности ответа сервера | 5500.22 / 10242.32 | 5173.32 / 10648.42 |
| От JSON браузера до возможности отрисовки | 7.05 / 15.85 | 7.00 / 15.00 |

request_ms — клиентское время HTTP-вызова, включая ожидание, получение полного ответа и служебную обработку. Это не чистое время GPU. TTFT — время до первого непустого content/reasoning delta; пустой служебный chunk не считается токеном. Для buffered-режима TTFT=null: задним числом восстановить его невозможно.

В текущем коде также добавлены отдельные initial_save/result_save и статусы каждой попытки валидации. Они появились после основного прогона. В отдельном реальном API-запросе запись реплики заняла 3,839 мс, запись результата — 10,316 мс, весь серверный цикл — 5991,664 мс. SQLite после повторного открытия вернула идентичное состояние. Это один дополнительный замер, не квантиль и не часть парного сравнения; файл evaluation/latency-storage-smoke.json. Основной прогон содержит суммарное storage_save. Сохранённая рекомендация содержит снимок диагностики движка до финальной записи; полный интервал записи и ответа находится в HTTP-заголовке и браузерном образце.

## Содержательное качество

Оценка выполнена ассистентом по явной экспертной рубрике, а не независимым руководителем продаж; режимы при оценке не скрывались. Шесть критериев по 0–2: контекст, ценность вопросов, следующий коммерческий шаг, естественность, подтверждённость данных, уважение ограничений. Максимум 12. Отсутствующая или скрытая фраза получает 0 за доставленный результат; оценка её содержания не имитируется.

Средний балл доставленного результата по всем 16 ситуациям: **10.06/12** против **8.12/12**. Только среди доступных уместных результатов: 10.06 против 9.29. Это описательная оценка одного прохода, не доказательство причинного влияния streaming на интеллект.

Основные обнаруженные дефекты:

1. После «никаких вопросов» оба варианта всё равно предлагают выбрать; валидатор пропускает вопрос, сформулированный повелительно без вопросительного знака.
2. Потоковый ответ дважды переносит условие «старт без опыта» с одного продукта на другой. Наличие правильной ссылки на каталог не гарантирует смысловую достоверность всей фразы.
3. При бюджете 10000 оба продолжают подбор, хотя самый дешёвый подтверждённый вариант стоит 12000. Нужно прямо учитывать отсутствие подходящего предложения.
4. После последнего согласованного уточнения потоковый ответ предлагает ещё уточнять обучение; после явного изменения цели снова предлагает более сложный вариант.
5. Текущий ответ считает два часа в неделю «реально мало» без подтверждённой нагрузки; другой делает слишком широкое утверждение о гарантиях любой школы.
6. В потоковом unsupported_guarantee валидатор скрыл фразу по unverified_commercial_amount. Исходная отклонённая фраза в этом API-прогоне не сохранялась, поэтому её смысловую корректность не устанавливаем.
7. Один потоковый вызов не уложился в 125 с ожидания. Точная причина не установлена. Настроенный HTTP read-timeout не следует считать общим дедлайном всего потокового ответа: получение промежуточных данных может продлевать обработку.

Эти дефекты зафиксированы, но коммерческие правила и промпт в этой диагностической итерации не переписывались.

## Карта Product Sales Intelligence

Файлы: [структура Excel](knowledge-design/excel.sales-map.synthetic.json), [пояснения](knowledge-design/README_RU.md).

Связи: основной продукт → аудитория → профессиональная цель → потенциальная потребность → диагностический вопрос → подтверждение клиента → возможность продукта → критерии выбора варианта.

Пример: администратор с простым отчётом → самостоятельность → базовые таблицы/формулы/фильтры. Общая мечта о росте сама по себе не обосновывает дорогой вариант. Регулярное объединение файлов → проверка структуры → потребность в автоматизации → соответствующая возможность, только если она подтверждена реальной программой.

Все сущности имеют стабильные ID; карта содержит сигналы и контрсигналы потребностей, вопросы с влиянием на выбор и условиями пропуска, связи с аргументами, критерии достаточности и ограничения. Цены, длительность, нагрузка, практика на личных файлах и куратор реальной школы неизвестны и оставлены null. approved_for_production=false. Карта не импортируется рабочим приложением.

## Следующий разумный эксперимент — не реализован

- Оставить основную конфигурацию без изменений. Отключать thinking повторно бессмысленно.
- Сначала уменьшить объём обязательного ответа и противоречия, вызывающие коррекцию: сейчас около 7,4 тыс. входных и 1 тыс. выходных токенов на запрос. Измерить компактный контракт отдельно на том же наборе с ручной проверкой потерь памяти и стратегии.
- Для потокового режима до внедрения проверить общий дедлайн, отмену запроса и восстановление. Не показывать менеджеру частичный непроверенный JSON только ради красивого TTFT.
- Если подключать карту продаж позже, выбирать релевантные связи по ситуации, а не прикладывать всю расширяемую карту к каждой реплике.
- Повторить сравнение в нескольких временных окнах и нескольких проходах, включая реальные длинные контексты с разрешения на их обработку. Один n=16 недостаточен для надёжного хвоста и доказательства «без потери качества».
