# Sales Intelligence Benchmark (офлайн)

Запуск из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --out work/benchmark-empty
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --out work/benchmark-mock --mode mock
```

Каталог результата должен быть новым/пустым. По умолчанию режимы офлайн; только явный --allow-paid читает существующую конфигурацию и разрешает API.
15 сценариев синтетические. Названия Eduson/Skillbox — контекст; каталог вымышленный, не реальные условия школ.
Два оригинальных многоходовых диалога не обнаружены в проверенных evaluation-артефактах. Найдены синтетические fixtures и отдельные ответы, недостаточные для достоверного восстановления исходных разговоров. Они не импортированы как A/B-результаты.

A воспроизводит raw Analysis через текущий process_turn с валидаторами и восстановлением. До двух raw_outputs на случай коррекции; недостаток ответа отмечается invalid. B независим: три поля decision/reason/say_to_customer, без плана A. inputs.json содержит подготовленные входы, ожидаемые действия не передаются моделям. Поля памяти заданы вручную одинаково, исторические model-derived планы не подмешиваются: измеряется решение на контрольной точке, не накопление памяти с нуля.

Импорт реальных ответов:
```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --out work/benchmark-real --saved responses.json --model MODEL_ID
```
responses.json — список объектов: scenario_id, scenario_hash (из inputs.json), variant A/B, origin real/mock, model, generation {temperature:0.2,max_tokens:3000,thinking:"disabled"}, source_id. Для A: raw_outputs — массив полных исходных JSON Analysis, включая коррекцию если нужна. Для B: output с тремя строками. Не используйте ответы другой ситуации/модели; происхождение real — заявление импортирующего, не автоматическое доказательство. metrics необязателен: latency_ms,input_tokens,output_tokens,cost_usd только реальные измерения всего получения ответа (включая повторы A). Секреты/заголовки/HTTP-дампы не импортировать. Время офлайн-повтора не считается latency модели.

Версия commit, состояние дерева и хеши текущих файлов фиксируются: dirty-дерево не выдаётся за чистый commit. Настройки — план эксперимента, не прочитанная локальная конфигурация. Идентификатор реальной модели обязателен при импорте. Сетевой исполнитель описан ниже; получение ответов требует отдельного разрешения.

Слепая оценка: эксперту передайте только blind_review.csv; private_mapping.json и results.json оставьте у организатора. Порядок вариантов перемешан воспроизводимо. При mock-прогоне таблица только для проверки экспорта. Пустые ответы не оценивать. Семь критериев: commercial_priority,context,novelty,naturalness,deal_progress,product_accuracy,safety.
Шкала каждого: 0 — неприемлемо/противоречит сценарию; 1 — серьёзные недостатки; 2 — частично полезно, требуется существенная правка; 3 — хорошее действие, небольшие замечания; 4 — точное, обоснованное и готовое к использованию. Критические нарушения вписывайте отдельно в critical_violations независимо от балла. Подробное обоснование — notes. Отсутствующие ответы не равны нулю.

```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --out work/benchmark-real --review reviewed.csv
```
Средние описательные; оценка не заменяется валидатором или самооценкой DeepSeek. Сравнивайте полные пары на одинаковых случаях и сохраняйте критические нарушения. При отсутствии реальных ответов/экспертных оценок коммерческое сравнение не выполнено.

## P1.2: ограниченный пилот

```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --pilot --out work/p12-dry --max-calls 12
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --multiturn --out work/p12-multi-dry --max-calls 24
```

Платный запуск только после разрешения пользователя:
```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --pilot --cases income video program no_catalog --out work/p12-live --allow-paid --max-calls 12
```

8 запросов без повторов, максимум 12 с коррекциями A. Лимит общий, проверяется перед транспортом; неисполненные варианты отмечаются not_run. B не имеет повтора. Используются текущие LLM_MODEL/LLM_MAX_TOKENS из уже настроенного .env, temperature=0.2, thinking disabled для обеих сторон. Подключение не меняется. Денежного лимита нет: ограничены число запросов и max_tokens; без актуального тарифа стоимость не вычисляется. Dry-run показывает плановый потолок выходных токенов при 3000; живой запуск использует фактическую настройку. Входные токены до запуска неизвестны.

Адаптер ObservedProvider переиспользует CompatibleProvider._complete, включая HTTP timeout. A проходит process_turn, B получает только minimal_prompt и общие данные. Исходные content сохраняются до разбора схемы; finish_reason, response_model, usage сохраняются отдельно. Успешные ответы доступны даже при последующей ошибке валидации. Ошибки сети сохраняют только тип, без HTTP-тела. Секрет ключа удаляется из сохраняемых данных. Производственные промпты и механизмы не изменяются.

Четыре пилотных случая расширены из income/video/program/no_catalog; последние два соответствуют запросу программы после нескольких вопросов и заинтересованному клиенту без каталога (не просьбе прислать условия). Восемь multi_* — фиксированные префиксы одного синтетического диалога, рекомендации не подставляются в речь. Каждая точка стартует с одинаковой вручную заданной памятью; это не тест накопления состояния A между вызовами. Различия схемы ответа, промпта и восстановления — часть сравниваемых подходов, не идеально изолированный эксперимент.

partial_results.json сохраняет каждую завершённую пару «сценарий/вариант»; после окончания доступны results.json, blind_review.csv, private_mapping.json, execution_plan.json. Каждый ответ содержит raw_responses, validation/validation_trace (если доступны), diagnostics, metrics и независимый product_audit. Автоматический аудит лишь выделяет подозрительные суммы/обещания; все продуктовые утверждения требуют ручной проверки по approved_claims для A и B. Отсутствие флага не означает безопасность.

diagnostic_category заполняется экспертом: MODEL_DECISION, PROMPT_OR_CONTEXT, VALIDATOR_BLOCK, RECOVERY_DEGRADATION, KNOWLEDGE_GAP, OTHER, UNKNOWN. Это гипотезы причин, не доказанная причинность. Эксперт сначала оценивает blind_review.csv без результатов трассировки и соответствия вариантов. Для анализа блокировок организатор затем использует приватные трассы. До реальных ответов оценки пусты, победитель не определяется.

## P1.3: прерывание и возобновление

Новые платные запуски создают run_state.json и manifest.json до первого запроса. Журнал содержит хеши кода и сценариев, модель, настройки, seed, общий лимит и результаты. Перед HTTP-запросом атомарно резервируется вызов; после получения сохраняется исходный ответ, затем результат контрольной точки. Записи JSON сохраняются через временный файл, flush/fsync и os.replace. Остаточный .tmp не считается завершённой записью. API-ключ в журнал не входит.

Состояния: running (может означать аварийный обрыв), interrupted (перехваченное исключение), completed/completed_with_errors. При перехватываемом аварийном завершении сохраняются тип исключения и частичный summary.json. При завершении процесса ОС обработчик может не выполниться: ориентируйтесь на run_state.json. .run.lock исключает одновременный запуск; после принудительного завершения оператор может удалить оставшийся lock только убедившись, что старый процесс завершён. Удаление lock не разрешает повтор неопределённого запроса.

Без оплаты проверить журнал:
```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --pilot --out work/NEW_RUN --resume
```
Продолжить новый журнальный запуск после отдельного разрешения (тот же каталог, сценарии, код, модель, настройки и исходный общий лимит):
```powershell
.\.venv\Scripts\python.exe -m experiments.sales_benchmark.run --pilot --out work/NEW_RUN --resume --allow-paid --max-calls 12
```

Любая сохранённая контрольная точка, включая ошибочную, не повторяется. Если активная точка содержит хотя бы один зарезервированный вызов, её автоматический повтор запрещён даже при сохранённом сыром ответе: требуется отдельный разбор, а не повторная оплата. Лимит между запусками не сбрасывается и не увеличивается через --resume.

Старый work/p12-live/partial_results.json не изменяется. У него нет манифеста и журнала запросов; --resume откажет до API. Последняя подтверждённая запись video B, пять ответивших API-вызовов. Отсутствие program A не доказывает отсутствие отправки. Нельзя восстановить точное число возможных незаписанных вызовов или причину остановки по этому файлу. Для дальнейшего запуска сначала сверить неопределённые обращения с журналом провайдера и отдельно согласовать новый эксперимент; нельзя считать его продолжением с доказанной идентичностью версии.

Диагностика video A (production НЕ изменён): сериализованная Pydantic-схема делает SalesPlan.need_depth необязательным nullable/default null; CompatibleProvider требует непустое значение. Intelligence.sales_plan также optional в схеме, но обязателен для живых реплик. Первая попытка прошла Pydantic, затем получила missing_depth. ValueError не имеет errors(), поэтому feedback.fields был пуст; текст требовал полный путь. Во второй попытке need_depth/priority_thread оказались внутри intelligence, что действительно нарушает additionalProperties=false. JSON синтаксически корректен в обеих попытках. $ref однозначно задаёт вложенность; доказательств ошибки сериализации нет.

Предлагаемый минимальный будущий production-diff, не применён: создавать отдельное представление схемы живого ответа перед отправкой (required intelligence, intelligence.sales_plan, sales_plan.need_depth, non-null для этих объектов/поля), сохранив совместимость модели хранения; для Missing sales_plan.need_depth передавать fields=[{path:["intelligence","sales_plan","need_depth"],type:"missing"}] и явно требовать поля внутри sales_plan. Не переносить поля автоматически и не ослаблять extra_forbidden. Это устранит подтверждённое противоречие требований, но не гарантирует соблюдение схемы моделью.
